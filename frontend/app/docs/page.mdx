# Documentation

llms-text generates an `llms.txt` file for a website.

`llms.txt` is a Markdown file a site publishes at its root — `example.com/llms.txt`. It names
the site and lists the pages worth reading. The convention is defined at
[llmstxt.org](https://llmstxt.org).

A model reading a site through a crawler receives navigation, cookie banners, footers and
duplicated boilerplate alongside the content. An index of the pages that carry the content is
smaller and faster to read.

> **What a run produces.** A run discovers a site's URLs and fetches up to 100 pages. It
> writes two files: `llms.txt`, an index, and `llms-full.txt`, the page text. A run writes a
> listing. Review it before publishing.

A run passes through seven stages. Each stage is described below, in the order it executes.

## Input

A website record holds one seed URL. The URL is absolute, `http` or `https`, and at most 2,048
characters. Its host is at most 253 characters.

A URL carrying credentials (`user:pass@host`) is rejected. A leading `www.` is preserved, so
`www.example.com` and `example.com` are separate records. One account holds one record per
origin. Two accounts can each hold a record for the same origin.

## Discovery

Discovery collects candidate URLs from the site itself. It reads four sources in order:

1. `/sitemap.xml`
2. `/sitemap_index.xml`
3. Every `Sitemap:` line in `/robots.txt`
4. The `<a href>` links on the seed page

The first source returning at least one same-origin URL wins. Source 4 runs only when the
first three return nothing, and it reads the seed page alone — no second level, no recursion.
It keeps same-origin links and stops at 10,000.

Discovery fetches at most 5 sitemap documents and accepts at most 50,000 URLs. It spends at
most 25% of the run's byte budget, which is 12.5 MiB. It reads `<loc>`, `<lastmod>` and
`<priority>`, and follows a sitemap index one level down. A document containing a `<!DOCTYPE`
declaration is refused before parsing.

Every other `robots.txt` directive is ignored. A failure at any source is logged and skipped.
Discovery returns an empty list on total failure, and the run continues with the seed page
alone.

This ordering is not novel. [Firecrawl](https://firecrawl.dev) and most tools that turn a site
into an `llms.txt` read the sitemap first and fall back to page links, because a sitemap is the
site's own statement of what it considers canonical and costs one request to read. Discovery
here follows that shape and departs from it in three places: it never recurses past the seed
page, where a general crawler follows links to a configured depth; it does not supplement the
frontier with search results or with pages cached from an earlier run; and it reads
`robots.txt` for `Sitemap:` lines rather than as a set of rules to obey. The borrowing is more
literal further down the pipeline — the prompt under Summarize is Firecrawl's, word for
word.

## Selection

Selection turns discovered URLs into the fetch list. It normalizes each URL, drops URLs by
rule, scores the survivors, sorts them, and caps the result.

Eleven drop rules apply in a fixed order: unparseable, duplicate, seed, off-origin, dated
archive, taxonomy, pagination, feed, changelog, localized duplicate, and over-limit. A dated
archive is a path segment holding a year from 1990 to 2099. A taxonomy path contains a segment
such as `tag`, `category` or `author`. A localized duplicate sits under a locale prefix whose
unprefixed form ranked higher and was already selected.

Scoring starts at zero. The site root adds 6.0. A path segment such as `docs`, `guide`,
`reference` or `api` adds 4.0. Each path segment subtracts 1.0. A sitemap `priority` moves the
score by up to ±1.0. A `lastmod` moves it by up to ±0.2, measured against the other URLs in
the same run. Equal scores break on the URL string, so a repeat run of an unchanged site
selects the same pages.

## Fetch

Fetching runs under six caps: 100 pages, 5 minutes, 50 MiB, 10 seconds per request, 5
concurrent requests, and 200 ms between requests.

Every URL passes an SSRF check before a socket opens. The check requires an `http` or `https`
scheme, port 80 or 443, and no embedded credentials. It resolves the host and refuses the URL
when any resolved address is private, loopback, link-local, multicast, reserved, or a cloud
metadata address. It resolves the host once and connects to that address. One resolution
closes the window in which a name changes between the check and the connection.

Redirects are followed for up to 5 hops. Every hop is checked again before it is followed. A
redirect from `https` to `http` is refused. Response bodies are counted against the byte
budget as they stream, so a declared `Content-Length` is never trusted.

## Extract

trafilatura parses each fetched page's HTML. It returns the main content as Markdown —
headings, prose, lists, tables and code blocks. Navigation, headers, footers and cookie
banners are discarded.

The title comes from JSON-LD, then `og:title`, then a lone `<h1>`, then `<title>`. The
description comes from the page's meta description. Either can be absent.

A page whose extracted body is under 200 characters is marked empty. Empty pages are omitted
from `llms.txt`.

## Summarize

A configuration flag gates this stage. The deployed service sets `CRAWL_ENRICH_WITH_LLM` to
`false`, so the stage is inactive. Each page keeps the title and description that extraction
produced, and a run completes without calling a model.

Where the flag is `true`, each page's first 4,000 characters go to Claude Haiku 4.5. The model
returns a 3–4 word title and a 9–10 word description for that page. Ten requests run at a
time, under 15 seconds per request and 90 seconds for the stage. A page whose request fails
keeps its extracted title and description. The archived page data keeps the extracted values
under either setting.

## Output

A run writes two files.

`llms.txt` is the index. It opens with one `#` heading naming the site and one blockquote
counting the pages. Each following `##` section holds one `- [title](url): description` line
per page. Sections run `Docs`, `Guide`, `API`, `Reference`, then the remaining groups
alphabetically, then `Other`.

`llms-full.txt` holds the same pages in the same order, each followed by its full Markdown. A
page is trimmed at 50 KiB. The document is trimmed at 5 MiB, always at a page boundary. A
trimmed file records the trim on its last line.

Both files are on a finished run's **Output** tab, with line numbers, a **Copy** button and a
**Download** button. A download is named after the site — `llms-example-com.txt` for
`https://example.com` — so saving several of them overwrites nothing. Rename the file to
`llms.txt` and publish it at the site's root, where it answers as plain text at
`https://example.com/llms.txt`. Where the file goes depends on the host: a `public/` or
`static/` directory for most frameworks, the site root for anything served from disk.

Runs are retained. Open an older run from the **Runs** tab to read the file it produced.

## Adding a site

The field on the [home page](/) takes an absolute URL. The URL carries its scheme:
`https://example.com`. Pressing Enter sends two requests: one registers the website, one
starts its first run.

The browser then opens the site's page with a run showing as **pending**. That page updates
itself as the run progresses. Nothing needs refreshing.

Submitting a URL the account already holds opens that site. The **Run now** button on a site's
page starts another run at any time.

## Schedules

A schedule repeats a run without a person pressing anything. A website carries at most one
schedule, set through `PUT /websites/{id}/schedule`. Four intervals are available: hourly,
every 6 hours, daily, and weekly.

A scheduler tick runs every 60 seconds and claims up to 50 due schedules. Each fire time after
the first is offset by up to ±5% of the interval. That is about ±3 minutes on an hourly
schedule and ±72 minutes on a daily one. The offset keeps sites added in one sitting from
crawling in the same second forever.

A schedule can be switched off without being deleted. Its run history outlives it.

## Limits

Every run executes inside fixed caps, and two more caps apply per account. They are listed
here so nobody discovers one by hitting it.

**Per run**

- **100 pages** — the most a single run fetches.
- **50 MiB** — the total downloaded across the run (52,428,800 bytes), counted across
  discovery and fetching together.
- **5 minutes** — the crawler's wall clock. The job runner stops a job at 10 minutes.

The page and byte caps are budgets. Reaching one part-way through ends the run with the pages
already collected, so a large site yields a partial file and a `completed` run.

Two cases fail a run outright. The first is a seed page that cannot be fetched. The second is
a seed page over the byte cap, which reports "The site's response was too large." A run
stopped at 5 minutes is cut off mid-flight.

A run gets 3 attempts when it fails on a request timeout, a transport error, or a storage
upload failure. The two retries wait 10 seconds and 60 seconds. Every other failure is
permanent and ends the run at the first attempt.

**Per account**

- **2 concurrent manual runs** — a third waits for one of them to finish.
- **50 runs per rolling 24 hours** — counting manual and scheduled runs together.

Exceeding either cap is answered immediately with a message naming the cap. The daily cap also
reports when it resets. The concurrent cap reports no time, because it clears when a run
already in flight finishes. The daily cap refuses further manual runs while schedules keep
firing. A busy schedule can therefore spend a budget a manual run is then refused for. Nothing
is queued behind a cap and nothing is silently dropped.

## API

llms-text is a FastAPI service. It publishes interactive OpenAPI documentation generated from
the code that serves each endpoint.

Every endpoint requires a Supabase JWT in an `Authorization: Bearer` header. Read endpoints
are unscoped: a signed-in caller reads every website and every run. Write endpoints check
ownership and answer `403` to anyone else.

Two endpoints return a run's files as plain text:

- `GET /runs/{id}/llms.txt`
- `GET /runs/{id}/llms-full.txt`

Each answers `404` while the run is pending, processing, or failed.
