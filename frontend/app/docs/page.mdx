# Documentation

Everything llms-text does, in one page.

> **Where this is up to.** llms-text is being built in the open, and the part that turns a
> site into a useful index is the part that is not finished. A run fetches **only the URL you
> gave it** — following links to the rest of the site is not built yet — and writes a
> **placeholder** `llms.txt` that lists what it fetched rather than a written summary of it.
> Everything around that works today: adding a site, running a crawl, watching it, and
> collecting the file it produced. Each section below says where its own part stands.

## What is llms.txt

`llms.txt` is a small Markdown file a website publishes at its root — `example.com/llms.txt` —
that tells a large language model what the site is and which of its pages are worth reading.
The convention is described at [llmstxt.org](https://llmstxt.org).

The problem it solves is that a model reading a site through a browser or a crawler gets
navigation, cookie banners, footers and duplicated boilerplate along with the content, and has
to guess what matters. A hand-written index of the pages that do matter is smaller, cheaper to
read, and says what the site's author would have said if asked.

llms-text is being built to write that file for you. Today it fetches the URL you give it and
produces a placeholder `llms.txt` naming what it fetched. The two parts that would make the
file worth publishing — discovering the rest of the site's pages, and reading them to work out
which carry the content — are the next milestone and are not built yet.

## Adding a site

Paste a URL into the box on the [home page](/) and press Enter. It has to be an absolute
`http://` or `https://` URL — `https://example.com`, not `example.com`.

That does two things: it registers the site, and it starts the first crawl immediately. You
land on the site's page with a run already showing as **pending**, and the page updates itself
as the run progresses — there is nothing to refresh and nothing else to press.

Pasting a URL you have already added takes you straight to it rather than reporting an error.
Two people can each add the same site; one person cannot add it twice.

## Manual vs scheduled runs

A **run** is one crawl of one site. A run is either manual or scheduled, and both produce the
same thing.

**Manual runs work today.** The **Run now** button on a site's page starts one. Adding a site
starts one too. Use it after you have changed the site and want the file regenerated.

**Scheduled runs work too, but there is no screen for them yet.** A schedule repeats a run at
a fixed interval, and there are four intervals — these are the only four:

- **Hourly** — a site that changes through the day: a changelog, a status page.
- **Every 6 hours** — an active documentation site.
- **Daily** — most sites.
- **Weekly** — a site that rarely changes: a marketing site, a personal page.

The API accepts a schedule and a timer fires the due ones, so a schedule set through the API
does run. What is missing is the **Schedule** tab that would let you set one without touching
the API — until it lands, that tab is a placeholder. A schedule can be switched off without
being deleted, its run history outlives it, and its runs count against the daily limit below
exactly as manual ones do.

## Reading the output

A finished run's `llms.txt` is on the site's **Output** tab, with line numbers, a **Copy**
button and a **Download** button. The download is named after the site — `llms-example-com.txt`
for `https://example.com` — so that saving several of them does not overwrite one file; rename
it to `llms.txt` when you publish it.

Publish it at the root of your site, so it answers at `https://your-site.com/llms.txt` as
plain text. Where the file goes depends on your host — a `public/` or `static/` directory for
most frameworks, the site root for anything served from disk. Bear in mind what the callout at
the top says: what a run writes today is a placeholder, not an index worth serving.

Runs are kept, so you can open an older one from the **Runs** tab and see what the file looked
like before a change.

## Limits

Every crawl runs inside fixed caps, and there are two per-account caps on top of them. They
are listed here so nobody has to discover one by hitting it.

**Per crawl**

- **100 pages** — the most a single run will fetch.
- **50 MiB** — the total downloaded across the whole run (52,428,800 bytes).
- **3 minutes** — how long a run gets. The crawler's own budget is 5 minutes, but the job
  runner stops a job at 3, so 3 is the number that actually bites.

The page cap is a budget rather than a failure: reaching it ends the run with the pages it
already had, so a large site yields a partial file instead of no file at all. It is also the
one cap you cannot reach today — a run fetches a single page — so it is really the ceiling
that starts applying once link discovery lands.

The other two are blunt, and worth knowing about before you meet one. Going over 50 MiB
**fails** the run right now, with "The site's response was too large": a run fetches one page,
and when the only page is the one that overran there is nothing partial left to keep. (Once a
run fetches many pages, busting the budget partway through will stop it the way the page cap
does.) And a run stopped at 3 minutes is cut off mid-flight rather than wrapped up neatly.

**Per account**

- **2 concurrent runs** — you can have two manual runs in flight at once. A third has to wait
  for one of them to finish.
- **50 runs per day** — across a rolling 24 hours, counting manual and scheduled runs
  together.

Going over either one is answered immediately, with a message naming the cap you hit. The
daily cap also says when it resets; the concurrent one does not, because "when a run you are
already waiting on finishes" is not a time anybody can predict. Nothing is queued behind a cap
and nothing is silently dropped.
