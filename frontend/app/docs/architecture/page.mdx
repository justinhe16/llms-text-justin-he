llms-text runs as four deployed pieces, talking to each other over an HTTP request/response
path and a queue.

## Shape

Vercel serves the Next.js App Router and the route handlers under `app/api/[...path]/`.
Fly.io runs one Docker image as two processes — `app`, the FastAPI service, and `worker`, the
ARQ job runner — scaled independently of each other. Supabase is Postgres, Auth, and Storage.
Upstash Redis holds the ARQ queue the worker polls.

The worker can call the Anthropic API to summarize a page. `CRAWL_ENRICH_WITH_LLM` is `false`
in the deployed service, so it does not — which is why the diagram draws that edge dashed
rather than animated: nothing travels along it today.

## Request path

A browser never calls Fly directly. It requests a same-origin Next.js route under
`app/api/[...path]/`, which forwards the request to FastAPI, server-side. That proxy is the
only place a Supabase access token is read from the session and attached to an outbound
request, and it happens entirely on the server — which is also why there is no CORS
configuration anywhere in this repository, and why `API_URL` is a server-only variable, never
prefixed `NEXT_PUBLIC_`.

The proxy bounds the upstream call at 30 seconds and answers `504` itself when that budget
runs out, rather than letting Vercel's own function-execution limit kill the request
mid-flight.

## Queueing a run

A run is queued from two entry points. A person presses **Run now**, or a scheduler tick
fires: it runs every 60 seconds, at second 0, and claims up to 50 due schedules in one pass.
Both paths do the same two things in the same order — commit the `runs` row, then enqueue the
job.

That ordering, not the reverse, is where an orphaned `pending` row comes from: a crash between
the commit and the enqueue leaves a row with nothing acting on it. It is also why the reaper
sweeps a `pending` run once it has sat unqueued for 10 minutes. The worker itself polls Redis
for work every 5 seconds.

## Concurrency

The backend runs on asyncio — one event loop per process, and no threads anywhere in it. A
crawl bounds its own requests in flight with `asyncio.Semaphore(5)`; a politeness gate
serializes request *starts* 200 ms apart across the whole run, independent of how many
requests are in flight; and the crawl itself runs inside a 300-second wall-clock timeout, with
arq's 600-second job timeout behind it as the outer backstop for a job wedged somewhere that
timeout does not cover.

Several of those concurrent requests can trip a shared cap — the page count, the byte budget —
at the same moment. The check-and-set that records which cap fired is lock-free: nothing
between the check and the set awaits, so the event loop cannot hand control to another task in
the middle of it, and exactly one cap gets recorded no matter how many tasks reach it
together.

One worker machine runs at most 2 jobs at a time — a crawl, a scheduler tick, and a reaper
pass all draw from that same limit.

## Data

asyncpg runs every query at runtime. Prisma's job stops at the schema and its migrations — it
never runs against the production database. Each process, the API and the worker separately,
builds its own connection pool of 2 to 10, so the two together can hold up to 20 connections
to Postgres, not 10.

A completed run's two artifacts, `llms.txt` and `llms-full.txt`, live directly in the
`runs.llms_txt` and `runs.llms_full_txt` text columns. The full fetched corpus — every page's
markdown, gzip-compressed, newline-delimited JSON — is uploaded to Supabase Storage
separately, at `crawl-payloads/{website_id}/{run_id}.jsonl.gz`. That upload happens before the
transaction that records its path, never inside one: a database transaction here never spans a
network call.

## Failure handling

A run stuck in `processing` is worse than a run that failed outright. The duplicate guard
refuses to start a new run for a website while one is already in flight, so a run that never
finishes blocks that website's every future trigger — each one answers `409` against a run
that is never coming back.

A run gets 3 attempts. The first two failures defer the next attempt by 10 seconds, then 60.
A failure is retried only when it is a request timeout, a transport error, or a Storage upload
failure; everything else — including an exception the classifier has never seen — is treated
as permanent, on the theory that an unrecognized failure is far more likely to be a bug than a
blip.

A reaper runs every 5 minutes and cleans up two kinds of stranded run: a `processing` run whose
worker claimed it more than 15 minutes ago, and a `pending` run more than 10 minutes old with
nothing behind it. It acts on up to 100 rows per pass.

## Trade-offs

- **Why asyncio rather than threads or Celery.** The work is I/O — DNS, TCP, TLS, HTTP. One
  event loop runs five requests concurrently in one thread's memory. ARQ is asyncio-native and
  shares the process's own loop and its `httpx` client; Celery would add a second broker
  protocol and a second serialization format for two job types.
- **Why trafilatura extraction runs on the event loop.** It is synchronous CPU work called
  from the fetch path, and it blocks the loop for the length of one parse. That is acceptable
  behind a 200 ms politeness gate at 100 pages: the loop already has 200 ms of slack per page
  start, and a parse is well under it. What it costs is that one pathological page delays
  every other request already in flight.
- **Why discovery stops at the seed page.** The caps bind before depth does — 100 pages, 50
  MiB, 5 minutes. A second level of links on a typical documentation site produces more URLs
  than the page cap admits, so recursion would change *which* 100 pages are fetched, not how
  many; and selection's ranked top 100 of a sitemap beats an arbitrary breadth-first 100.
- **Why reads are unscoped and only writes are ownership-checked.** This system is not
  multi-tenant. Read endpoints require a JWT and do not filter by user; write endpoints check
  ownership as soon as the resource is fetched. The cost, stated plainly: any signed-in caller
  can read any run's files.
- **Why artifacts are served from Postgres columns rather than Storage.** Reading one is a
  query the API already makes. Storage would be a second network call and a signed URL to
  manage for a value already sitting in the row. What it costs: `llms-full.txt` is bounded at
  5 MiB, so a single completed run can carry 5 MiB in one column.
- **What breaks first under 100× load.** The single Fly worker, capped at 2 concurrent jobs.
  Next, the Postgres connection budget — pool size is set per process, not shared, so the API
  and the worker each add up to 10 of their own. Then `runs` itself, growing by up to 5 MiB
  for every completed run.
- **What would change first.** Artifacts would move to Storage with signed URLs; extraction
  would move off the event loop; and rate limiting would move to the edge, per user — today's
  two abuse caps are counted per request and are check-then-act rather than atomic.
