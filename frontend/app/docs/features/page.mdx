This tab is what things are, and how you use them: the website/run/schedule model, adding a
site, keeping it current on a schedule, watching its output change over time, the limits that
bound every run, and the API underneath all of it. For the seven stages a run passes through,
see [How a run works](/docs). For what's deployed and why, see
[Architecture](/docs/architecture).

A run's trigger is `manual` or `scheduled`. Its status moves `pending` → `processing` →
`completed` or `failed`.

Turning a schedule off, or deleting it, does not touch the runs it already started. A deleted
schedule's runs keep their own history — only the reference to the schedule is cleared. Run
history outlives the schedule that produced it.

## Adding a site

The field on the [home page](/) takes an absolute URL. The URL carries its scheme:
`https://example.com`. Pressing Enter sends two requests: one registers the website, one
starts its first run.

The browser then opens the site's page with a run showing as **pending**. That page updates
itself as the run progresses. Nothing needs refreshing.

Submitting a URL the account already holds opens that site. The **Run now** button on a
site's page starts another run at any time.

## Schedules

A schedule repeats a run without a person pressing anything. A website carries at most one
schedule, set through `PUT /websites/{id}/schedule`. Four intervals are available: hourly,
every 6 hours, daily, and weekly.

A scheduler tick runs every 60 seconds and claims up to 50 due schedules. Each fire time
after the first is offset by up to ±5% of the interval — about ±3 minutes on an hourly
schedule, ±72 minutes on a daily one. The offset keeps sites added in one sitting from
crawling in the same second forever.

A schedule can be switched off without being deleted.

it reports on the artifact — what `llms.txt` looks like, and what changed in it — rather than
on the crawler's own timing.

failed, or still in progress). A "What changed in the latest run" panel names the added,
removed and changed pages. Total runs and success rate sit below all of it, in one line
rather than as tiles of their own.

7d is the default. Every bucket, in every window, is a UTC hour or a UTC day — the panel says
so once rather than converting to the reader's own time zone, so a bucket's label always
matches the instant it covers.

Each chart decides its own emptiness. The outcomes chart is empty only when the window has no
runs at all. The index size and index changes charts can still be empty with runs in the
window — a run whose comparison wasn't recorded, or that predates this window's own history,
contributes no point to either.

A website that has never been crawled shows a prompt to run one instead of an empty panel.
That distinction comes from the site's run history, not from this endpoint: every field it
returns is scoped to the selected window, so on its own it cannot tell "nothing in this
window" apart from "nothing, ever."

## Limits

Every run executes inside a fixed set of caps, and two more apply per account. This is the
complete list — [How a run works](/docs) and [Architecture](/docs/architecture) each keep
only the numbers their own argument needs, and link back here for the rest.

Pages and bytes are budgets, not thresholds that abort the run. Reaching one ends the run with
what it already has, so a large site yields a partial file and a `completed` run.

Three cases fail a run outright instead: a seed page that cannot be fetched; a seed page over
the byte cap, which reports "The site's response was too large."; a seed page the site's own
`robots.txt` disallows, which reports "This site's robots.txt disallows crawling this URL."
and is never fetched at all. A run stopped at 5 minutes is cut off mid-flight, not failed.

Retries apply to a request timeout, a transport error, or a Storage upload failure. Every
other failure is permanent — one attempt, then the run fails.

Exceeding either cap answers immediately, naming the cap. The daily cap also says when it
resets; the concurrent cap doesn't, because it clears the moment a run already in flight
finishes. A busy schedule can spend the daily budget a manual run is then refused for —
schedules keep firing regardless. Nothing is queued behind a cap, and nothing is silently
dropped.

## API

llms-text is a FastAPI service. It publishes interactive OpenAPI documentation generated from
the code that serves each endpoint.

Every endpoint requires a Supabase JWT in an `Authorization: Bearer` header. Read endpoints
are unscoped: a signed-in caller reads every website and every run. Write endpoints check
ownership and answer `403` to anyone else.

Two endpoints return a run's files as plain text:

- `GET /runs/{id}/llms.txt`
- `GET /runs/{id}/llms-full.txt`

Each answers `404` while the run is pending, processing, or failed.
